### 1.3 测试策略（为什么可信）

## 2. 平衡验证

### 2.1 方法

`tests/balance-sim.js` 与冒烟测试共用同一套「真实引擎 + 桩 UI」驱动方式，四种玩家策略 × 四个角色 × 400 局 = **6400 局**（`perCell=400`，seed 基 12345），全部使用种子化 PRNG（可复现）。

| 策略 | 含义 | 建模的玩家 |
|---|---|---|
| 随机 | 可用选项均匀随机 | 完全不看内容的第一次试玩 |

### 2.5b 状态密度旋钮实测（`stateChanceFactor` 的能力边界）

同一 seed 序列（seed 基 = 1，perCell=400）下只改 `CONFIG.stateChanceFactor`：

| factor | 全局状态/局（四策略均） | 理性（满 25 段） | 随机 | 同屏峰值 |
|---|---|---|---|---|
| **0.4（现状）** | 1.19 | 1.56 | 1.71 | 2 |
| 0.9 | 2.68 | 3.46 | 3.85 | 2 |
| 1.0 | 2.98 | 3.85 | 4.30 | 2 |
| 2.0 | 5.11 | **6.47** | 7.46 | 2 |

**结论修正（重要）**：
1. 有人据此得出「factor 上限只有 3.0，永远到不了设计的 5-7 次」——**这个结论不成立**。`stateChanceOf()` 对 `base × factor` 做 `min(1, …)` 截断，因此 factor ≥ 2 时每次遭遇必然命中，实测理性策略可到 **6.47 次/局**，5–7 次在数学上可达（约 factor 1.5–1.8 即可摸到 5 次）。
2. 但**靠 factor 硬拉上去是退化状态**：相当于"每次遇到带状态的选项都必挂状态"，与 v5 设计意图（"不能让状态成为照单发放"）直接冲突。
3. 设计文档 §1.4 的「正面 5-7 次、负面 1-2 次」是**静态估算**（25 段 × 36% 带状态选项 × 0.6 ≈ 5.4），没有计入 order 窗口偏向——带状态的选项集中在 order 35–52，单局实际遭遇次数远低于 36% 的静态占比。**要"有感但不机械"地达到 5-7 次，正确做法是提状态选项密度（数据侧），而不是只拧 factor。**
4. 渐进路线（推荐）：v5.1 先 `factor → 0.9`（理性 3.46 次/局，玩家明显感知到状态存在，且同屏仍为 2）；若要贴近 5-7，再给 8–12 个日常事件挂状态、把情感向事件的 `stateChance` 由 0.5 提到 0.7。

### 2.10 方案 C 的结局顺序副作用 → C+ 变体实测（本轮新增的关键发现）

方案 C 落地时把 `end_lurker` 放在了**数组第 1 位**（所有结局之前）。这在语义上有一个没人注意的连带后果：**结局判定是"从上到下第一个 match 命中"**，所以一条「挂过潜水 flag、relation ≤40」的局，即使它真实的崩坏原因是**心情见底或声望见底**，也会先被 `end_lurker` 抓住。也就是说，潜水大师在数组首位会**吸收其他人的崩坏局**。

为量化这一点，我用同一份代码的临时副本（不改仓库）做了三组对照，全部 `perCell=400`、seed 基 12345，**与 §2.4 同批可比**：

| 变体 | 结局顺序 | `end_lurker` | `zero_energy` | `zero_mood` | `zero_fame` | `zero_relation` | 可达 |
|---|---|---|---|---|---|---|---|
| **C 现状（lurker 首位）** | lurker → energy → mood → relation → fame → … | **1084（16.9%）** | 1903 | **40（0.6%）** | **6（0.1%）** | 599 | 12 |
| C 错位（lurker 排最后） | energy → mood → relation → fame → **lurker** → … | **57（0.9%）** | 1904 | 95 | 13 | 1563 | 12 |
| **C+（推荐）** | energy → mood → **fame → lurker → relation** → … | **1012（15.8%）** | 1904 | **95（1.5%）** | **25（0.4%）** | 596 | 12 |

> 注意 C+ 的目标排列里 **`end_zero_fame` 在 `end_zero_relation` 之前**——这跟当前仓库的 `relation → fame` 顺序是反的。详见下面的「落地方式」。

分策略看（沉默策略落 `end_lurker` 的比例）：C 现状 **62.6%** → C+ **58.3%**（933/1600）→ C 错位 **0.4%**（7/1600）。四策略崩坏率（24.3 / 0 / 99.1 / 100）与平均段数在三组里**完全不变**。

**读法**：

1. **C 现状的副作用量级**：`end_zero_mood` 95 → 40（−55 局）、`end_zero_fame` 13 → 6（−7 局），合计 **62 局 = 全场的 0.97%**。即「每 100 局里有 1 局：玩家其实是心情/声望撑不住散场的，却被判成"潜水大师"」。`end_zero_energy` 只被吸收 1 局，可忽略。
2. **C 错位（把 lurker 挪到 relation 之后）是无效功**：`end_lurker` 直接掉回 0.9%、`zero_relation` 回到 1563 —— 因为 relation 归零时 `end_zero_relation` 先命中，方案 C 等于没做。**这说明 lurker 必须排在 `end_zero_relation` 之前**，这一条是硬约束。
3. **C+ 消除的是「lurker 73 局误判」，不是「零副作用」**（此处已按 engineering-lead 的复现修正，我自己也做了归因实测）：
   - **lurker 让出的 72 局去哪了**：`end_zero_mood` +55、`end_zero_fame` +7、`end_zero_energy` +1、`end_zero_relation` +9 —— 这 72 局都是「真实崩坏原因被潜水大师顶掉」的误判，C+ 把它们**全部还给了正确的崩坏结局**。
   - **但 C+ 新引入一处改判**：把 `end_zero_fame` 提到 `end_zero_relation` 之前后，**终局时 fame 与 relation 同时归零**的局会改判。我用插桩数过：这种局**全场共 12 局（0.19%）**，三种顺序下的归属是——

     | 顺序 | 这 12 局的归属 |
     |---|---|
     | 基线（lurker 在最后） | 查无此人 12 |
     | **C 现状** | 潜水大师 **9** + 查无此人 **3**（其中 9 局被 lurker 抢走） |
     | **C+** | 群聊隐身人 **12** |

     即：C+ 让这 12 局**从「查无此人」改判「群聊隐身人」**（相对基线），相对 C 则是「lurker 9 + 查无此人 3 → 群聊隐身人 12」。这与 `fame 6→25`（+19 = 归还 7 + 改判 12）、`relation 599→596`（−3 = −改判 12 + lurker 回流 9）的算术完全闭合。
   - **所以准确表述是**：**「零 lurker 吸收」+「fame/relation 优先序反转 12 局（0.19%）」**。C 与 C+ 都自洽，区别只是「两个数值同时归零时先认哪个崩坏」——这属产品口味，不是纯技术优劣。
4. 代价极小：`end_lurker` 从 16.9% → 15.8%（−72 局），换个说法是"潜水玩法的兑现率从 62.6% 降到 58.3%，仍远高于任何其他策略"。

**落地方式（这里是坑，别照"挪到某条之后"写）**

C+ **不是一处移动，是两处**，因为当前仓库顺序是 `lurker → energy → mood → relation → fame`（`relation` 在 `fame` 之前）。若只把 lurker 挪到 `fame` 之后，得到的是 `energy → mood → relation → fame → lurker`，lurker 落到 `end_zero_relation` **后面**，就是上表的「C 错位」——**`end_lurker` 会静默退回 0.9%，方案 C 等于白做**。

正确做法：按**目标排列**直接写，不要按"某条之后"描述：

```
end_zero_energy → end_zero_mood → end_zero_fame → end_lurker → end_zero_relation → end_pet → …
```

即：① 把 `end_zero_fame` 提到 `end_zero_relation` **之前**；② 把 `end_lurker` 插到 `fame` 与 `relation` **之间**。`match` 条件不动、引擎 0 改动。

**配套断言（必须一起改，否则 164/1）**：现套件那条顺序不变式是**位置耦合**的（写死了"首位是 lurker、崩坏占 2–5 位"），在 C+ 下必红——我在临时副本实测过：**C+ 顺序下现套件 164 通过 / 1 失败，唯一红的就是这条**（其余 164 条与顺序无关，说明改动面确实只有这一处）。

改写建议（**我已在 C 与 C+ 两种顺序下各跑一次，都是 165/0 全绿**）：

```js
check('结局顺序契约：末位为兜底（match 为空），潜水大师早于「查无此人」，4 个崩坏结局的 match 均为 [0,0] 且项互不相同',
  (function () {
    const idx = id => GAME.ENDINGS.findIndex(e => e.id === id);
    const zeros = GAME.ENDINGS.filter(e => /^end_zero_/.test(e.id));
    const statOf = e => Object.keys((e.match || {}).stats || {})[0];
    return Object.keys(GAME.ENDINGS[GAME.ENDINGS.length - 1].match || {}).length === 0 &&
      idx('end_lurker') >= 0 && idx('end_lurker') < idx('end_zero_relation') &&
      zeros.length === 4 &&
      zeros.every(e => { const k = statOf(e); const r = ((e.match || {}).stats || {})[k];
        return ['energy', 'mood', 'relation', 'fame'].indexOf(k) >= 0 && r && r[0] === 0 && r[1] === 0; }) &&
      new Set(zeros.map(statOf)).size === 4;
  })());
```

> 关键差别：**不要断言"崩坏结局在数组里连续"**。C+ 下 lurker 就坐在 `fame` 与 `relation` 之间，崩坏块本来就被切成两段（`fame` 与 `relation` 不相邻）。engineering-lead 给的一版用「4 个崩坏 index 连续」判断，我实测**在 C 下绿、在 C+ 下红（164/1）**，不能直接用。上面这版把"是不是崩坏结局"表达为 `match` 语义（`stats: {某键: [0,0]}` + 四项互不相同 + lurker 早于 relation），与位置完全解耦。

### 9.3 已知非零副作用（**非完全无损**，必须标注）

方案 C 把 `end_lurker` 放在数组第 1 位，而结局判定是"从上到下第一个 match 命中"，因此以下局会被**吸收**：**挂过潜水 flag、`relation ≤ 40`，但这一局真正的散场原因是心情（mood）或声望（fame）见底**。

| 被吸收的结局 | 修复前 | 修复后 | 被吸收量 |
|---|---|---|---|
| `end_zero_mood`（绷断了） | 95 | **40** | **−55** |
| `end_zero_fame`（群聊隐身人） | 13 | **6** | **−7** |
| `end_zero_energy`（电量耗尽） | 1904 | 1903 | −1（可忽略） |
| **合计** | — | — | **62 局 = 全场的 0.97%** |

**结论：方案 C 是「12 结局全可达 + 潜水玩法兑现」，但不是「零副作用」。** 4 个崩坏结局里有 2 个被小幅让位，量级约 1%，玩家侧表现为"极少数心情/声望撑不住的局，结局文案写的是潜水大师"。`end_zero_fame` 本来就只有 0.1%（B-03 死内容），再让位后更接近不可见。

> 消除办法已有实测（§2.10 的 **C+ 顺序**，目标排列 `energy → mood → fame → lurker → relation`）：`end_zero_mood` 回到 95、`end_zero_fame` 回到 25、lurker 误判清零，代价是 `end_lurker` 16.9% → 15.8%、沉默玩法 62.6% → 58.3%，四策略崩坏率与段数不变。**但它不是零副作用**：把 `fame` 提到 `relation` 前，会让**终局时两句同时归零的 12 局（0.19%）从「查无此人」改判「群聊隐身人」**（插桩实测，§2.10 读法 3）。落地还要注意两件事：① 是**两处移动**（`fame` 前移 + `lurker` 插入），只挪 lurker 一处会退到 0.9%；② `smoke-test.js` 的顺序断言是位置耦合的，改顺序必须同步改写（§2.10 给了在 C / C+ 下都全绿的版本）。已列 §4 P0，**本轮未实施**（team-lead 已封闭本轮）。
